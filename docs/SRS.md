# Software Requirements Specification (SRS)

## 1. Purpose

This document specifies the functional and non-functional requirements for the Automated Anomaly Explanation with Counterfactuals prototype.

The system will analyze industrial machine observations, detect anomalies using Isolation Forest, and generate constrained counterfactual recommendations that explain how an anomalous observation could move into the detector’s learned normal region.

This specification governs the hackathon implementation. It is intentionally focused on a complete, testable baseline rather than a production-scale platform.

## 2. System Scope

The system consists of the following logical components:

```text
Raw dataset
    ↓
Data loader
    ↓
Preprocessing
    ↓
Isolation Forest detector
    ↓
Counterfactual generator
    ↓
Feasibility and plausibility checks
    ↓
Candidate ranking
    ↓
Explanation generator
    ↓
Evaluation and Streamlit demo
```

The system must use the AI4I 2020 Predictive Maintenance Dataset unless the project owner explicitly selects another dataset.

The system must not assume the precise dataset schema before the dataset has been inspected.

## 3. Intended Architecture

The implementation must preserve the following responsibility boundaries:

```text
src/data_loader.py       Load and validate the raw dataset.
src/preprocessing.py     Clean, encode, scale, and transform data.
src/detector.py          Train, save/load, score, and classify with Isolation Forest.
src/counterfactual.py    Search for minimal valid candidate changes.
src/feasibility.py       Check ranges, mutability, validity, and plausibility.
src/explanation.py       Generate clear explanation text from verified results.
src/evaluator.py         Calculate detector and counterfactual metrics.
src/pipeline.py          Coordinate one complete analysis request.
src/utils.py             Hold only shared reusable helper functions.
app/app.py               Provide the Streamlit user interface only.
```

The Streamlit application must call the pipeline. It must not contain detector training logic, counterfactual-search logic, or feasibility rules directly.

## 4. Definitions

### Observation

One row of machine data representing an operating state.

### Feature

An input variable used by the anomaly detector, such as a numerical sensor or operational measurement. Exact features are determined after data inspection.

### Identifier

A value that identifies an observation, product, machine, or record. Identifiers must not be treated as ordinary mutable operating features unless explicitly justified.

### Known label

A dataset-provided target or failure indicator retained for evaluation or analysis. It must not automatically be used as an input feature for unsupervised anomaly detection.

### Anomaly score

A numerical value generated by the anomaly detector representing how unusual an observation is according to the fitted model.

### Anomaly decision

The system classification of an observation as either `NORMAL` or `ANOMALY`, based on the trained detector and defined threshold.

### Counterfactual

A modified version of an anomalous observation that is classified as normal by the same trained anomaly detector.

### Valid counterfactual

A counterfactual that satisfies all hard constraints and changes the detector result from `ANOMALY` to `NORMAL`.

### Feasible counterfactual

A valid counterfactual that also respects feature mutability, permitted values, and configured valid ranges.

### Plausible counterfactual

A feasible counterfactual that passes the selected lightweight plausibility check against the normal-data region.

## 5. Functional Requirements

### FR-01: Load Raw Dataset

The system shall load the raw dataset from the project’s raw-data location.

The loader shall:

- accept the expected file type after the actual dataset is obtained;
- provide a clear error if the raw dataset is missing, unreadable, empty, or malformed;
- return a tabular dataset suitable for inspection;
- preserve original column names before any transformation;
- avoid silently dropping rows or columns;
- report basic loading information, including row count, column count, duplicate count, and missing-value summary.

### FR-02: Validate Dataset Structure

After loading, the system shall validate the actual dataset structure.

Validation shall include:

- detection of missing column names;
- detection of duplicated column names;
- detection of duplicated records where relevant;
- missing-value counts;
- inferred data types;
- candidate identifier columns;
- candidate label or failure-status columns;
- numerical versus categorical feature candidates.

The system shall not assume hard-coded required columns until the data dictionary is created from the inspected dataset.

### FR-03: Support Exploratory Data Analysis

The initial EDA workflow shall provide enough evidence to make data-design decisions.

It shall inspect:

- shape of the data;
- column names;
- data types;
- summary statistics;
- missing values;
- duplicates;
- distributions of numerical candidate features;
- class distribution of known labels, if present;
- observed minimum and maximum values;
- potential data leakage columns;
- potential immutable identifiers;
- candidate mutable operating features.

EDA findings shall be recorded in the data dictionary and used to configure preprocessing and feasibility constraints.

### FR-04: Define Feature Roles

The system shall classify dataset columns into roles after inspection.

Possible roles include:

- model input feature;
- immutable identifier;
- known evaluation label;
- metadata;
- unsupported field.

Each model input feature shall have a documented type and mutability status.

A feature must not be marked mutable without a reasonable domain justification.

### FR-05: Preprocess Data

The preprocessing component shall prepare selected model features for Isolation Forest training and inference.

It shall:

- handle missing values using an explicitly documented strategy;
- encode supported categorical features if they are selected for modelling;
- scale numerical model features using a reproducible fitted scaler;
- preserve the fitted preprocessing objects for later inference;
- apply exactly the same feature order and transformations during training and inference;
- provide a method to convert a transformed counterfactual back into understandable original units;
- reject inference input that lacks required model features or contains incompatible data types.

Preprocessing must not include known failure labels as model input features unless a future design change explicitly authorizes supervised learning.

### FR-06: Train Anomaly Detector

The detector component shall train an Isolation Forest model.

The training process shall:

- use only the configured model features;
- primarily fit the detector on observations designated as normal operational data, when known labels permit this split;
- preserve model parameters and the fitted model for reuse;
- document the training-data selection strategy;
- support a configured random state so results are reproducible;
- avoid training multiple advanced detectors during the initial baseline implementation.

### FR-07: Score and Classify Observations

The detector component shall provide a stable interface for inference.

At minimum, it shall support conceptual operations equivalent to:

```python
predict_anomaly_score(sample)
is_anomaly(sample)
```

For each observation, the system shall return:

- anomaly score;
- normal or anomaly decision;
- threshold or decision convention where meaningful;
- any validation error encountered.

The counterfactual engine must use this same detector interface. It must not use a different or inconsistent decision rule.

### FR-08: Generate Counterfactual Candidates

For an observation classified as anomalous, the system shall generate candidate counterfactuals through custom constrained search.

The initial search shall:

- begin with the original anomalous observation;
- vary only configured mutable features;
- keep immutable features unchanged;
- respect configured feature ranges and step sizes where applicable;
- query the trained detector for each candidate;
- prioritize small changes and fewer changed features;
- stop according to documented search limits, such as maximum candidates, maximum changed features, or time limit;
- return candidate metadata, not just values.

The initial baseline must not depend on DiCE or another counterfactual library. Such a library may be evaluated only after the custom baseline works and is tested.

### FR-09: Verify Counterfactual Validity

The system shall verify every candidate before presenting it to a user.

A candidate may be presented as valid only if:

```text
Original observation decision = ANOMALY
Candidate counterfactual decision = NORMAL
```

The system shall never claim that a candidate resolves an anomaly without rerunning the trained detector on that candidate.

### FR-10: Enforce Hard Feasibility Constraints

The feasibility component shall reject any candidate that violates hard constraints.

Hard constraints shall include:

- no missing values;
- no invalid numerical values;
- values within configured valid ranges;
- valid categorical values where relevant;
- immutable features unchanged;
- required input schema preserved.

Observed dataset ranges may be used as an initial constraint baseline only after the actual dataset is inspected. Any domain-specific ranges must be documented and justified.

### FR-11: Perform Plausibility Check

The system shall apply a lightweight plausibility check to feasible counterfactual candidates.

For the baseline, the plausibility method may be a documented distance-based or statistical method based on normal operational data.

The plausibility module shall:

- use a consistent method for all candidates in an experiment;
- return a numeric score or clear pass/fail result;
- document the chosen threshold or rule;
- avoid claiming causal or physical certainty;
- reject or penalize candidates that are too implausible under the selected method.

Complex causal modelling, density-estimation systems, or neural plausibility models are not required for the initial build.

### FR-12: Rank Candidates

The system shall rank verified candidate counterfactuals.

Ranking shall prefer, in this order unless later experiments justify a documented alternative:

1. Valid anomaly-to-normal flip.
2. Hard feasibility compliance.
3. Plausibility compliance or higher plausibility score.
4. Lower number of changed features.
5. Lower total normalized change from the original observation.
6. Lower generation cost or search complexity where candidates are otherwise comparable.

The selected best candidate must retain all ranking metadata.

### FR-13: Generate Human-Readable Explanation

The explanation component shall create text from actual detector and counterfactual results.

For an anomalous observation with a valid best counterfactual, the explanation shall include:

- anomaly status;
- anomaly score;
- each changed feature;
- original and recommended value for each changed feature;
- magnitude and direction of each change;
- number of features changed;
- detector status after applying the counterfactual;
- feasibility result;
- plausibility result;
- a concise interpretation of the recommendation.

The explanation must not:

- invent changed features;
- describe unmeasured causes;
- claim real-world machine failure certainty;
- claim physical feasibility beyond the implemented checks;
- claim a candidate is valid or plausible when the corresponding check failed.

For a normal observation, the explanation shall report that no counterfactual is needed.

For an anomaly with no valid candidate found within the configured search budget, the explanation shall say that no feasible counterfactual was found. It must not fabricate a recommendation.

### FR-14: Provide End-to-End Analysis

The pipeline component shall expose one end-to-end analysis operation conceptually equivalent to:

```python
analyze(sample)
```

The operation shall:

1. validate the input;
2. preprocess the observation;
3. score and classify it;
4. return a normal result immediately if the observation is normal;
5. generate counterfactual candidates if it is anomalous;
6. apply feasibility and plausibility checks;
7. rank valid candidates;
8. generate an explanation;
9. return structured results suitable for the UI and evaluation.

### FR-15: Evaluate the Detector

The evaluator shall measure detector performance where the dataset provides known labels suitable for evaluation.

Possible detector metrics include:

- precision;
- recall;
- F1 score;
- confusion matrix;
- anomaly-related metrics appropriate to the observed class balance.

Evaluation must clearly distinguish known dataset labels from the unsupervised detector’s predicted anomaly decisions.

### FR-16: Evaluate Counterfactual Quality

The evaluator shall run the counterfactual workflow over a sample of anomalous observations and measure:

- validity rate;
- average sparsity;
- average normalized proximity;
- plausibility pass rate or average plausibility score;
- average and maximum generation time;
- number of cases with no counterfactual found.

The project target is to test approximately 20 to 30 anomalous examples when sufficient applicable observations are available.

### FR-17: Provide Streamlit Demo

The Streamlit application shall provide a simple demonstration interface after the pipeline works.

The UI shall:

- allow a user to select or enter a supported observation;
- invoke the pipeline;
- display anomaly score and decision;
- display the recommended counterfactual when one exists;
- display before/after values for changed features;
- display feasibility and plausibility status;
- display the generated explanation;
- communicate clearly when a point is normal or no valid counterfactual is found.

The UI must remain a presentation layer and must not contain the core ML implementation.

## 6. Input Requirements

The system shall accept:

- the raw AI4I dataset file in the designated raw-data folder;
- individual observations with every required model input feature;
- values compatible with the feature data types defined after dataset inspection.

The system shall reject or clearly report:

- missing required fields;
- unexpected input types;
- invalid categorical values;
- values that cannot be processed;
- model inference before the required preprocessing objects and detector are available.

## 7. Output Requirements

The end-to-end analysis result shall contain structured information sufficient for display and evaluation.

For normal observations, output shall include:

```text
status
anomaly_score
detector_decision = NORMAL
message
```

For anomalous observations, output shall include:

```text
status
anomaly_score
detector_decision = ANOMALY
counterfactual_found
ranked_counterfactuals
best_counterfactual
changed_features
feasibility_result
plausibility_result
counterfactual_detector_decision
generation_time
explanation
```

The exact internal data structure may evolve, but these concepts must be available.

## 8. Non-Functional Requirements

### NFR-01: Reproducibility

The training and evaluation process shall be reproducible using documented configuration values, feature order, preprocessing objects, and model random state.

### NFR-02: Modularity

Each source module shall have one clear responsibility. The UI shall not duplicate ML logic.

### NFR-03: Transparency

The baseline counterfactual method shall be understandable and inspectable. Search constraints, scoring, and ranking criteria shall be documented.

### NFR-04: Performance

The system shall record counterfactual-generation time. For the hackathon demo, it should generate a result in a practical interactive timeframe for typical individual inputs, subject to documented search limits.

### NFR-05: Error Handling

Errors shall be clear and actionable. The system shall fail safely rather than silently returning misleading results.

### NFR-06: Honest Communication

The system shall communicate model-based recommendations, not guaranteed physical outcomes. Limitations of Isolation Forest, data coverage, and plausibility checks shall be documented.

### NFR-07: Maintainability

Configuration for model parameters, feature rules, ranges, search limits, and thresholds should be externalized where practical rather than scattered across source files.

## 9. Security and Privacy

The hackathon prototype uses a public predictive-maintenance dataset and does not require authentication, user accounts, personal data storage, databases, or network services.

If a future version introduces real operational data, privacy, access-control, data-retention, and security requirements must be defined separately.

## 10. Assumptions

- The AI4I dataset will be available locally before data loading and EDA begin.
- The dataset contains enough meaningful operating features to train a tabular anomaly detector.
- Known labels, if present, can be used for evaluation and normal-data selection but are not direct anomaly-detector input features.
- A lightweight plausibility approach is sufficient for the hackathon baseline.
- The system is a decision-support prototype, not a production safety-control system.
- The user will make implementation changes manually with assisted coding; generated code must be reviewed and tested module by module.

## 11. Explicit Exclusions

The following are not requirements for the initial version:

- production deployment;
- APIs or microservices;
- database schema or ERD;
- authentication;
- cloud infrastructure;
- deep learning;
- causal inference;
- LLM-generated core explanations;
- multi-dataset support;
- multi-domain support;
- elaborate frontend design;
- a comparison of many anomaly detectors.

## 12. Acceptance Criteria

The implementation is accepted only when all applicable criteria below pass:

- The raw dataset loads successfully and receives a documented inspection.
- The data dictionary identifies actual selected features, labels, types, ranges, and mutability.
- Preprocessing is fitted during training and reused unchanged during inference.
- Isolation Forest returns scores and decisions for valid inputs.
- An anomalous sample can be passed to the counterfactual engine.
- At least one returned counterfactual is verified by the same detector as `NORMAL`.
- Returned candidates do not change immutable features.
- Returned candidates remain in configured valid ranges.
- Returned candidates pass the implemented feasibility check.
- Plausibility results are shown and are not fabricated.
- Candidate ranking prefers valid, feasible, sparse, and close changes.
- Explanations reflect the actual returned values.
- Normal observations do not receive unnecessary counterfactual recommendations.
- No-counterfactual cases are reported honestly.
- Counterfactual metrics and generation time are calculated over the evaluation sample.
- The Streamlit demo shows the end-to-end result without embedding core ML logic in the UI.1
